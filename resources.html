01 / A SMALL, WORKING START

Your first
validated matrix.

Run the original example before you model a real project. The starter converts the Entities, Fields and Rules sheets into JSON. It does not reconstruct games or prove behavioral parity.

Before you start

  • Git and Python 3.10 or newer installed.
  • A terminal and a new working folder. If rustports already exists, use a different folder rather than overwriting it.
  • Excel or LibreOffice only if you want to edit the workbook.
  • No game, server, GitHub login or Rust compiler needed for this Python example.
Trusted local workbooks only. This experimental validator is not a sandbox or a public upload service. Review code before running it and never include secrets or third-party game files.
Read the starter documentation ↗
Windows · Command Prompt
git clone https://github.com/phoenixfire808/rustports.git
cd rustports\toolkit\spreadsheet
py -3 -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python scripts/build_matrix.py
.venv\Scripts\python scripts/build_matrix.py --check
.venv\Scripts\python -m unittest discover -s tests -v
macOS / Linux · Terminal
git clone https://github.com/phoenixfire808/rustports.git
cd rustports/toolkit/spreadsheet
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python scripts/build_matrix.py
.venv/bin/python scripts/build_matrix.py --check
.venv/bin/python -m unittest discover -s tests -v

What success looks like

You get generated/matrix.json with five original example rows. The --check command exits successfully without rewriting it, and the test suite reports OK.

Then copy the starter to your own project, preserve the example, and edit your copy of workbooks/model.xlsx. Fix data in the workbook, not in generated JSON.

If py is unavailable on Windows, use your installed Python 3.10+ executable. On Linux, your distribution may require its Python venv package. Do not use administrator privileges to work around dependency errors.

02 / SPREADSHEET-FIRST RESEARCH

Make the unknowns visible.

Reverse engineering starts with careful observation, not confident guesses. Work only with systems you are authorized to analyze. Keep evidence, hypotheses and implementation separate.

  1. 01 / OBSERVE

    Record the evidence.

    Define scope and permissions. Log the setup, action, observed result, source and confidence. Repeat the observation.

  2. 02 / MODEL

    Give facts stable IDs.

    Describe entities, fields and rules. Keep unsupported hypotheses in Evidence, not in runtime constants.

  3. 03 / GENERATE

    Validate before building.

    Export the matrix. Resolve ID, type and reference errors in the sheet. Let generic engine code consume it.

  4. 04 / VERIFY

    Test the real behavior.

    A valid matrix is not a correct game. Compare observable runtime behavior with your recorded reference and document differences.

The Evidence sheet is currently for human review, not automatic validation.Read the full method ↗

DEVELOPMENT SNAPSHOT

Native Jcode integration

The source snapshot is public for review. CLI dispatch, reference parsing and resource limits need work. No tested binary or stable native release is supplied with that legacy snapshot. A separate Windows JcodeSS preview now has five passing Obsidian sync tests and packaged CLI/SQLite smoke checks, but full interactive acceptance remains unverified.
